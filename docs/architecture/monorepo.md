# Monorepo Structure

> Part of the [architecture docs](architecture.md). Back to [README](../../README.md).

How the monorepo is laid out, what each part is for, and how to work in it. It was set up in issue #102; the frontend in `web/` was added in #107 and has its own guide, [web/README.md](../../web/README.md). The decisions behind it are in [ADR 0001: Monorepo](adr/0001-monorepo.md) and [ADR 0017: Python and FastAPI backend](adr/0017-python-fastapi-backend.md).

## 1. The big picture

- **One repository, many Python packages.** Five backend services and three shared libraries live in one repo and are managed together by **uv** as a *workspace*.
- **One lockfile.** `uv.lock` pins the exact version of every dependency for every package, so everyone (and CI, and the server) runs the same versions.
- **One environment.** `uv sync` creates a single `.venv/` at the repo root with every library, every service and the dev tools installed. You never `pip install` anything.
- **Each service is independent at runtime.** Services run as separate processes (later, separate containers), each with its own port, its own Postgres schema and its own database user. They only talk to each other through HTTP APIs and events, never by importing each other's code.

## 2. Folder layout

```text
COMP-4350-Group5-GetDrove/

├── .editorconfig           # Indentation and line endings for every editor
├── scripts/
│   └── check.sh            # Runs every check CI runs, in one go
├── libs/                   # Shared code used by several services
│   ├── common-web/         # (empty for now, #103) error responses, correlation IDs, logging
│   ├── common-security/    # (empty for now, #91) JWT validation, current user, roles
│   └── events/             # (empty for now, #104) event envelope, outbox, Redis Streams consumer
├── services/
│   ├── accounts/           # port 8001
│   ├── trips/              # port 8002
│   ├── routing/            # port 8003
│   ├── payments/           # port 8004
│   └── notifications/      # port 8005
├── web/                    # Next.js + TypeScript frontend, managed with npm (see web/README.md)
├── contracts/              # OpenAPI specs and event schemas (see contracts/README.md)
├── infra/                  # Docker Compose, Traefik, Postgres init (see infra/README.md)

```

The frontend is not part of the uv workspace: it has its own `package.json` and `package-lock.json` in `web/`, and its own checks (ESLint, TypeScript, Vitest). Its API types are generated from `contracts/openapi`, so the backend and frontend share one source of truth for every endpoint.

## 3. Inside one service (Trips as the example)

Every service has the same shape:

```text
services/trips/
├── pyproject.toml              # The service's dependencies + its architecture rules (import-linter)
├── README.md                   # How to run, test and migrate this service
├── alembic.ini                 # Alembic (database migrations) config
├── migrations/
│   ├── env.py                  # Connects Alembic to this service's schema and settings
│   ├── script.py.mako          # Template for new migration files
│   └── versions/               # Migration files go here (empty until the first table)
├── src/trips/
│   ├── domain/                 # Business rules. Pure Python only.
│   ├── application/            # Use cases, and ports.py (the interfaces they need)
│   ├── adapters/
│   │   ├── api/                # FastAPI routers and Pydantic request/response schemas
│   │   │   └── health.py       # GET /health
│   │   └── persistence/        # SQLAlchemy tables and repositories
│   │       └── tables.py       # metadata for the "trips" schema (no tables yet)
│   └── infrastructure/
│       ├── main.py             # create_app(): builds the FastAPI app and adds routers
│       └── settings.py         # Configuration from environment variables (TRIPS_*)
└── tests/
    └── test_health.py          # Calls GET /health in memory and checks the response
```

### The four layers (Clean Architecture)

Think of them as rings. Code may only depend **inwards**.

| Layer | What goes in it | May import |
|---|---|---|
| `domain` | Entities (e.g. `Trip`), value objects, rules ("seats must be 1–6"), domain errors | Nothing from other layers. No FastAPI, SQLAlchemy, HTTP, settings. |
| `application` | Use cases (e.g. `PostTrip`), and `ports.py`: `typing.Protocol` interfaces for anything external (repository, Routing client, event publisher) | `domain` only. Still no frameworks. |
| `adapters` | The outside world: FastAPI routers, Pydantic schemas, SQLAlchemy tables and repositories, HTTP clients to other services, event consumers | `application`, `domain`, frameworks |
| `infrastructure` | Startup and wiring only: the app factory, settings, connecting use cases to their adapters | Everything |

Why: the business rules can be tested with plain unit tests and in-memory fakes, without a database or a web server, and swapping a technology later only touches `adapters`.

### These rules are enforced automatically

Each service's `pyproject.toml` has two **import-linter** contracts:

1. **Clean Architecture layers:** `infrastructure → adapters → application → domain`. An inner layer importing an outer one fails the check.
2. **Domain and use cases stay framework-free:** `domain` and `application` may not import `fastapi`, `sqlalchemy` or `pydantic_settings`. When a service starts using `httpx`, `redis` or `stripe`, add them to that list (import-linter only accepts packages the service actually depends on).

Run from inside the service folder: `cd services/trips && uv run lint-imports`.

## 4. Settings and environment variables

Each service reads its configuration from environment variables with its own prefix, using pydantic-settings (`infrastructure/settings.py`):

| Service | Prefix | Example |
|---|---|---|
| Accounts | `ACCOUNTS_` | `ACCOUNTS_DATABASE_URL` |
| Trips | `TRIPS_` | `TRIPS_DATABASE_URL` |
| Routing | `ROUTING_` | `ROUTING_DATABASE_URL` |
| Payments | `PAYMENTS_` | `PAYMENTS_DATABASE_URL` |
| Notifications | `NOTIFICATIONS_` | `NOTIFICATIONS_DATABASE_URL` |

Defaults point at a local Postgres (`postgresql+asyncpg://<service>:<service>@localhost:5432/getdrove`). Copy `.env.example` to `.env` to override; `.env` is gitignored and must never be committed. When you add a setting, add it to `settings.py` **and** `.env.example`.

## 5. Database and migrations (Alembic)

- Each service owns one Postgres **schema** named after it (`trips`, `accounts`, …) and only ever touches that schema.
- Tables are defined in `adapters/persistence/tables.py` using the `metadata` object already there. It sets the schema and consistent constraint names.
- A **migration** is a small script that changes the database structure (create a table, add a column). Alembic keeps them in order in `migrations/versions/` and records which ones each database has run, so every laptop, test database and the live server end up identical.

Typical flow (needs the database from Docker Compose, #105):

```bash
cd services/trips
# 1. edit adapters/persistence/tables.py
uv run alembic revision --autogenerate -m "create trips table"   # 2. generate
# 3. read and fix the generated file in migrations/versions/
uv run alembic upgrade head                                       # 4. apply
uv run alembic downgrade -1 && uv run alembic upgrade head        # 5. check undo works
# 6. commit the migration with the code that uses it
```

Rules: only the service owner writes migrations for that service; never edit a migration after it's merged into `develop` (add a new one instead); PostGIS (`CREATE EXTENSION postgis`) is created by the Postgres init scripts, not by migrations.

## 6. Shared tooling (root `pyproject.toml`)

| Tool | What it does | Command |
|---|---|---|
| **Ruff** | Formatter and linter (line length 100, Python files only) | `uv run ruff format .` / `uv run ruff check .` |
| **mypy** | Static type checking in `--strict` mode on every package's `src/` | `uv run mypy` |
| **pytest** | Tests; async tests just work (`asyncio_mode = auto`) | `uv run pytest` or `uv run pytest services/trips` |
| **coverage** | Which lines the tests ran | `uv run pytest --cov` |
| **import-linter** | Architecture rules per service | `cd services/<name> && uv run lint-imports` |

`bash scripts/check.sh` runs all of them in the same order CI will. Run it before opening a pull request.

Ruff's lint rules include naming, import sorting, likely bugs, async mistakes and basic security checks. `assert` is allowed in tests.

## 7. Everyday commands

```bash
# First time (install uv first: brew install uv)
uv sync

# Run a service with auto-reload
uv run --package trips uvicorn trips.infrastructure.main:app --reload --port 8002
# then open http://localhost:8002/health and http://localhost:8002/docs (Swagger UI)

# Add a dependency to one service
uv add --package trips httpx

# Add a dev tool for everyone
uv add --dev respx

# Run everything CI runs
bash scripts/check.sh
```

After pulling changes that touch `pyproject.toml` or `uv.lock`, run `uv sync` again.

## 8. How to add things

**A new endpoint**
1. Domain rules in `domain/` (plain classes or dataclasses), with unit tests.
2. A use case in `application/` that takes its ports in the constructor; add any new Protocol to `application/ports.py`.
3. A router in `adapters/api/` with Pydantic request/response schemas; it calls the use case.
4. Include the router in `infrastructure/main.py` and wire the use case to its adapters there.
5. Tests: unit tests for domain and use case (with fakes), an API test like `tests/test_health.py`.

**A new table:** see section 5.

**A shared helper used by several services:** it belongs in `libs/`, not copied between services. Discuss with the team first, since every service depends on `libs/`.

## 9. Conventions worth knowing

- **Ports per service:** Accounts 8001, Trips 8002, Routing 8003, Payments 8004, Notifications 8005. Locally only; behind Traefik they'll be reached as `/api/<service>/…`.
- **Every service has `GET /health`** returning `{"status": "ok", "service": "<name>"}`. Docker, Traefik and the deploy smoke test use it.
- **Services never import each other.** If Trips needs something from Routing, it calls Routing's API through a client in `adapters/` that implements a port.
- **Each package has a `py.typed` file,** which tells mypy the package ships type information.
- **Test files** sit in each package's `tests/` folder. pytest uses `importlib` mode, so test files in different services can share names (e.g. every service has `test_health.py`).
